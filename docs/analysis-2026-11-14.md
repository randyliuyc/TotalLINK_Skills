## 三、架构与设计

### 3.1 三层职责切分（这是全仓库最正确的决定）

```
┌───────────────────────────────────────────────┐
│ 场景 Skill（知识层）                            │
│ model-designer / formbuilder / app-help / …    │
│ 只写"怎么判断、按什么顺序做、什么算完成"          │
└──────────────┬────────────────────────────────┘
               │ 通过 tlk 命令组调用
┌──────────────▼────────────────────────────────┐
│ base Skill（传输层）totallink-base              │
│ 配置·令牌·POST·错误归类。不认识任何场景           │
└──────────────┬────────────────────────────────┘
               │ 插件契约 GROUP / register()
┌──────────────▼────────────────────────────────┐
│ HTTP：linkDMAIAction / linkDMExport /           │
│       linkDMRun / linkDMImport                 │
└───────────────────────────────────────────────┘
```

关键设计：`scripts/tlk.py:115` 的 `discover_plugins()` 扫同级目录找 `tlk_group.py`，**base 完全不认识 model-designer**。目录不在，命令组自然消失（无兜底、无报错）。这是一个干净的插件契约——本次实测 `tlk --help` 自动出现 `model` 组，删除目录即消失，符合设计。

### 3.2 知识的四层沉淀

| 层 | 载体 | 回答什么问题 | 上下文成本 |
|---|---|---|---|
| 决策层 | `SKILL.md` | 现在该做哪一步、什么算做完、错了怎么办 | 常驻（3.7~20.8KB/个） |
| 契约层 | `references/*.md` | 这个字段能不能这么写、影响哪个端 | 按需读（1.6~15KB/个） |
| 实例层 | `samples/`（43） | 照着抄哪个 | 按需读 |
| 语料层 | `samples-corpus/`（674） | 这个写法在生产里出现过吗 | grep，不进上下文 |

这个分层是有意识的——`model-designer/SKILL.md:120-142` 有一张「任务 → 必读文档」表，把"该读哪份"变成显式路由，而不是让 agent 猜。这一节是整份 SKILL.md 里最有价值的 20 行。

### 3.3 五处值得学的设计

**第一，把不确定性写成硬规则。** `model-designer/SKILL.md:39-56` 的 10 条硬规则里，第 0 条是"任务书门禁"——未确认任务书不许生成 XML；第 8 条是"不臆造"——列名只准从 `model dict` 的清单选。这正是 LLM 最容易翻车的地方，它用流程约束住了。

**第二，错误码是一等公民。** `AUTH / NETWORK / BIZ / PARAM / CONFIG / IO / HTTP / UNKNOWN` 八类，每类都有对应的排查动作，而不是一句"调用失败"。`tlk_core.py:173-207` 的 `_post` 把它们统一收口，调用方不需要判断异常类型。

**第三，"探不到就问，不试探"的升级。** HEAD 提交（`7c97b7f`）把 `model dict` 的参数缺省全删了——原来有默认编号，现在缺配置直接报 `CONFIG` 并列出缺哪几项，要求问用户。`tlk_group.py:154-167` 的实现说明了理由：猜错编号会得到 500 或空列，把"环境未开通"误判成"参数不对"，越试越远。这是从踩坑里长出来的设计。

**第四，服务端 warning 不等于错误。** `tlk_core.py:254-264`：响应 `action="warning"` 时服务端先降速再正常返回，脚本只往 stderr 打一行、不非零退出，并在结果里加 `_warning`。SKILL.md 用一整节教 agent"别把它当超时"。这类"平台怪癖的显式建模"通常只在生产里被捶过才写得出来。

**第五，两层验收，且明确"agent 不声称已验证"。** `model-designer/SKILL.md:78-83`：可执行断言（validate 无 error、run 列对齐）agent 自己跑；人工断言（APP 列表渲染、FB 表单回写）列给用户实机确认，**agent 不得声称已验证**。这条边界划得很清楚。

### 3.4 知识分层里的重复

`totallink-app-help` 和 `model-designer` 之间有一块职责重叠区：模型 H5 模板的客户端约定。目前是"app-help 持有权威、model-designer 指过去"——`model-designer/SKILL.md:135,140` 明确写"属性级细节见 `../totallink-app-help/references/`"。方向是对的（单一事实源），但**跨 skill 的相对路径在单 skill 安装时会断**（见 §4.2）。

## 四、问题清单

按"会不会造成实际损害"排序，不按发现顺序。

### P0-1 `--project` 指定不存在的项目时，静默跑到了另一个项目（实测）

```bash
$ HOME=/tmp/h1 python3 scripts/tlk.py auth verify --project "不存在的项目"
{
  "error": "AUTH",
  "message": "令牌无效或已过期，请检查项目 '测试' 的 auth_token",
  "_project": "测试"          ← 问的是"不存在的项目"，用的却是"测试"
}
```

原因在 `scripts/tlk_core.py:88-97`：传入的项目名不在 `projects` 里时，`if project_name and project_name in projects` 不成立，代码落到 `active` 分支，再落到"第一个项目"兜底。

后果：多项目环境下（README 明确支持多项目），用户或 agent 用 `--project B` 想操作 B 环境，实际打到了 A 环境。**对 `model import` 这类写操作，这会把模型导进错误的环境**，而且返回 `status: ok`，不看字段看不出问题。

修复：显式传了 `project_name` 但命中不到时返回 `CONFIG`，不要回退。兜底只应在"完全没传"时发生。

### P0-2 令牌文件权限 0644（实测）

```bash
$ ls -l /tmp/h1/.totallink/config.json
-rw-r--r--  1 ...  141 ... config.json
```

`tlk_core.py:65-69` 的 `save_config` 直接 `open(..., "w")`，跟随系统 umask。这个文件里是 `"auth_token": "tlk_..."`——SKILL.md 自己写了「配置文件的 `auth_token` 等价于账号口令」（第 46 行），同一仓库里 `smtp.json` 要求 `chmod 600`，但**令牌文件没有**。同机其他用户可读。

顺带一个同源问题：`tlk.py:195` 的 `env add --token "tlk_..."` 让令牌经命令行传递，会留在 shell history 和 `ps` 输出里。建议支持 `--token-stdin` 或读 `TOTALLINK_TOKEN`。

修复：`save_config` 里用 `os.open(path, O_WRONLY|O_CREAT|O_TRUNC, 0o600)`，或写完 `os.chmod(path, 0o600)`。

### P0-3 校验器的 error 级与真实语料冲突（实测）

对 674 个生产模型跑 `validate`，出现 5 个 error 级诊断：

| 模型 | 诊断 | 结论（2026-11-14 维护者逐条确认后） |
|---|---|---|
| `ERAQA202010X#701-图片.xml` | `CUBE_COLNAME`：DMCubeSetting 缺 COLNAME | 该条为 `CAPTION=图片 / COLTYPE=LANGUAGE-zh`，同列另有正常的 `LINKLABELPICTURE` en/zh 一对；条目本身无效但不阻断 → **降 warning** |
| `ERAQA202010X#700-Instument choose.xml` | `MODELSETTING_JSON` | 原文是**单个 DEL 控制字符（0x7F）**，属字段损坏而非规则误判 → **删除该语料**，规则不动 |
| `ERAQA101510X#504-Scan Code.xml` | `PARATYPE_ILLEGAL`：`TEXTAREA` | 全语料仅 1 例（`ParaLabel04="Scan "`、必填，脚本 `N'{3}'`）；引擎不因词表外取值拒导入 → **降 info，词表不补** |
| `KEEWAYZUPSCH05#10-BOM管理.xml` | `PARATYPE_ILLEGAL`：`字符型` | 全语料仅 1 例（同模型其它参数均为英文类型）；同上 → **降 info** |
| `ERAQA301010X.COPY#10-Copy Inspection Result.xml` | `PARAM_INDEX_UNDEFINED`：`{10}` 超出上限 | **本文判断错误**：`{10}` 是系统传入的调用方文本框内容，不是第 11 个用户参数 → **校验器差一错误，`{10}` 合法** |

**两处订正**（初版这两条判断是错的，保留痕迹以便追溯）：

其一，初版说 `MODELSETTING_JSON` 的"文案与级别自相矛盾"。看到原文后要修正：内容是 0x7F，属损坏数据，判 error 是有道理的；矛盾只剩在契约层——error 声称"导入会被拒"，而 0x7F 大概率照常导入、只是配置为空。处理上采纳维护者意见：删语料，不放宽规则。

其二，初版把 `{10}` 判为"真缺陷"。实际 `{0}`~`{9}` 对应用户参数 01~10（0 基），`{10}` 由系统传入调用方文本框的内容。校验器原来的 `idx >= 10` 是差一错误，正确边界是 `> 10`，且 `10` 还需显式放行，否则会掉进 `PARAM_INDEX_UNDEFINED` 的 warning 分支。**教训是我按 `placeholders.md` 的"0 基、参数 01~10"反推语义时，把没有文档化的系统参数当成了越界；语料里 `{10}` 仅 1 例、无 `{11}` 以上，其实已经暗示了边界。**

去掉这四条误判后，`error` 级剩下的含义就干净了。这仍是个**语义校准问题**，影响面不小：error 级一旦掺入"其实能跑"的项，agent 就学会了不信任 error，硬规则的约束力会被稀释。校准后 error 数从 5 降到 0，`validate` 可以作为"交付前必须为 0"的硬断言使用——这也是把它写进回归测试的前提。

| `description` 说明"做什么 + 何时用" | 8/9 合格；base 只有"是什么"，无触发词 | base 的 description 仅 70 字符，缺少"当用户要调用 TotalLINK 工具/查额度/配令牌时使用"这类触发语；它恰恰是最该被选中的那个 |
| description 长度 ≤1024 字符 | 全部合格（最长 321） | 良好 |
| Progressive disclosure（SKILL.md 轻，细节进 references） | 结构上做得很好 | 但单文件偏重：`formbuilder` 20.8KB、`reimbursement` 19.8KB、`model-designer` 18.0KB（155 行内塞满表格） |
| 相对路径可移植 | 部分跨 skill 引用是"仓库根相对" | 需修（P1-6） |
| 非标准 frontmatter 键 | `slug` / `repo` / `setup` / `metadata.workbuddy` | 无害，但 `setup.required` 暗示一个并不存在的安装器，容易被误读 |
| 脚本与文档同步 | `validate` 的诊断码表在 SKILL.md 与代码里各一份，目前一致 | 靠人工维护，容易再次漂移 |
| 安全约定显式化 | 有专门章节："禁止远程覆盖"、"SMTP 600"、"收件人不硬编码" | 这是加分项，很少见 skill 会写自己的供应链安全规则 |

**上下文成本提醒**：`model-designer/SKILL.md` 18KB ≈ 8~9k tokens，`formbuilder` 20.8KB ≈ 10k tokens。若两个 skill 同时在场，光 SKILL.md 就占掉 ~20k。建议把 model-designer 的「错误怎么读」大表（第 85-118 行，约 3.4KB）挪进 `references/errors.md`——它只在出错时才需要。

## 六、上手与交接指南

### 6.1 五分钟跑起来

```bash
# 1. 拿一份能用的 Python（3.9+，本仓库零第三方依赖）
python3 --version

# 2. 配置一个项目（令牌 tlk_ 开头，向管理员要）
python3 scripts/tlk.py env add "开发环境" --token "tlk_xxx" --url "http://<host>:8088"

# 3. 自检：能打出项目/URL/用户/额度四项就算通
python3 scripts/tlk.py auth verify

# 4. 找工具、调工具
python3 scripts/tlk.py tools search 报销
python3 scripts/tlk.py call LINKAI20 10 --script-type 0 --params-json '["", "2026-06-01", "2026-07-11", ""]'

# 5. 模型侧（需要 SystemAdmin / SystemExpert 角色）
python3 scripts/tlk.py model validate <file.xml>          # 纯本地，不走网络，先跑这个
python3 scripts/tlk.py model run <code> <num> --params-json '[]'
```

失败先看 `error` 字段，不要看 message：`CONFIG` 找配置，`AUTH` 换令牌，`NETWORK` 查地址，`BIZ` 看 message 原文。

### 6.2 我要改 X，该动哪个文件

| 想改的东西 | 改这里 | 注意 |
|---|---|---|
| 新增/调整一个工具调用动作 | `SKILL.md` 命令表 + `tlk_core.py` | 命令组插件化，别把场景逻辑塞进 base |
| 模型 XML 某个字段能不能这么写 | `model-designer/references/fields.md` | 同时看 `validate_model.py` 有无对应诊断码 |

| 某标记（`--LINKxxx`）的语义 | `references/link-flags.md` | 每条必须带 `file:line` 溯源 |
| 某个环境怎么消费某字段 | `references/runner-behavior.md` §7 | 运行器/APP/FB 三张反向清单 |

### 6.3 新增一个 skill 的检查清单

1. 目录名 = frontmatter `name`，全小写连字符。
2. `description` 里写清**触发语**（"当用户……时使用"），这是唯一参与选中的文本。
3. `SKILL.md` 只放决策与流程；契约、大表、样例放 `references/`。
4. 跨 skill 引用一律写 `../<skill>/references/xxx.md`，不写仓库根相对路径。
5. 需要联网/写操作/发邮件，在 `SKILL.md` 顶部写"安全约定"节。
6. 凡是"平台行为"的断言，带 `file:line` 或语料文件名。

### 6.4 维护者三条纪律（仓库里已经写了，值得继续执行）

1. **更新 Skill 禁止远程覆盖**：`SKILL.md:23-38` 要求 clone 到 `/tmp`、逐文件 diff、用户同意后才落地。技能文件是可执行代码，自动覆盖等于把远程仓库变成执行通道——这条判断是对的。
2. **反直觉结论必须亲自复核**：`docs/handoff-formbuilder-app.md:104-108` 记录了一次"手册勘误其实是自己读错"的教训，并定下"所有勘误结论必须贴原文行号"。
3. **语料零命中 ≠ 弃用**：`handoff:108`。这条防止把"没搜到"误判成"不存在"，是知识库长期维护的关键心态。

## 八、值得保留的判断力

有几点是"分析者容易忽略但确实做对了"的，写下来避免后续重构时被改掉：

`validate` 对未知情况一律走 warning 而非 error——`check_placeholders` 里对未定义的 `{N}` 只报 warning，理由写在 `validate_model.py:342-344`：附加模型本来就可能由调用方传参，判 error 会误伤。这是**知道自己的规则边界在哪**，比规则本身更重要。

`model dict` 宁愿报 `CONFIG` 让 agent 去问人，也不内置默认编号（`tlk_group.py:23-25` 的注释解释了为什么）。在一个"多连接多库并存"的环境里，把猜测权交还给用户是对的。

`reimbursement-audit` 把"发邮件"设成必须人工确认的不可逆动作，并把"md 报告生成后必须停下"写成默认节奏（`SKILL.md:33`）。这类"给 agent 设置刹车"的写法，在其他 skill 里应该复用。
